Text input

The control a person types into: a name, an amount, a date, an email, a search. It is where the manual path lives, and the manual path is a locked decision rather than a fallback, so this is not a second-class control.

Atom8 grey pages2 axes5 states, both themes

Anatomy

One zone and one value, which is what makes it an atom. Everything below is drawn by design/system/components/text-input.css through the same entry point a product screen loads, so this page cannot drift from the screens: there is no second copy of the CSS here to drift from.

  • .input the atom itself: a full width box with a 44px floor, a control radius and a one pixel edge. It is a real input, never a styled span, and step 6 gave it the class in place of the bare .field input selector
  • border-color reads --line-control. This edge is the whole of the control's identity: the fill is paper and so is the card behind it, so nothing else says a control is here
  • min-height reads --tap, the 44px floor the project holds everywhere. Never overridden downward
  • ::placeholder reads --text-muted. It is a hint about the format, never the label: a placeholder that carries the label disappears the moment a person starts typing
  • [aria-invalid] the authored invalid state, hooked on the native attribute so no screen needs a new class
  • label, .hint not this atom. They belong to the Form field molecule, which is not built yet, which is why they render bare above. When field.css lands they take their 12px muted form and nothing here changes

The money field carries one more thing inside the same box, the currency sign, and that is a variant rather than a second anatomy: the box, the edge, the radius, the floor and the ring are the ones above, unchanged and measured. It is .affix, below.

The control is width: 100% of its field, so its width is always the column's. On a product screen that column is the 560px form measure; the stage above is .kit-stage.col, which hands the field the same whole width. A component that carries no width of its own is a component that cannot be wrong about one.

Variants and sizes

Two axes, and they are different in kind. Type changes no pixel at all: it changes the keyboard a phone offers and what the browser will autofill. The sign changes exactly one measurement, the left padding, and it is the only variant of this atom a person can see. There is no size axis: every input in the product is 44px tall at 14px, on all 8 grey pages and all 14 coloured ones, and the census measured that as one value on every property. Width is deliberately not an axis either: 100% against auto is layout, so the email field on Settings and the amount field in a form column are the same input.

Set by what is being typed, never by how it should look. It changes the keyboard a phone offers and what the browser will autofill, and it changes nothing about the paint. Getting it wrong costs a person keystrokes on the one screen where typing is the whole job

The sign

Set by the UNIT of the value, and there is one unit in this product that goes inside the box: money. A currency sign belongs to the amount itself, so it stands where the amount stands and a person never types it. Any other unit is prose about the field and belongs to the label or the hint above and below it

$

The sign is not a control and is not a second value. It carries aria-hidden="true", it is not in the tab order, and it takes pointer-events: none, so a click on it lands on the input underneath and the caret goes where the person aimed. The accessible name of the field is still "Amount", from the label, and a screen reader is not told "dollar" twice.

There is no textarea in this product, on any of the 55 pages, so it is not a variant of this atom and it is not a hole in it. Nothing in Tendd asks a person to write a paragraph. If a screen ever does, that is a new component with its own decisions about height and resizing, and it is authored rather than extracted, the same way the invalid state below was.

When to use it

A text input is where a person tells the product something it cannot know: the name of a service that is not in the catalogue, an amount, the date of the next payment, the email an account hangs on. It is the whole of D2, the locked decision that manual entry is an equal second path and not a punishment for refusing a bank connection. That is why the form is short: four fields on add-subscription, two on Settings, one on sign-in. Every extra field on that screen is a reason to close the tab, and the category field was cut for exactly that reason.

What a person types is the value and nothing else. The Amount field asks for digits, so it takes digits: the currency sign is ours to draw, the decimal point is theirs to type, and a person is never asked to know which of "$17.99", "17.99 USD" or "17,99" we were hoping for. That is the whole of the .affix variant, and it is the reason it exists on this atom rather than as a formatter somewhere later.

Labels come from voice/docs/microcopy.md and are plain nouns in the person's words: "Name", "Amount", "Billing frequency", "Next payment date", "Email", "Find a service". The hint underneath teaches a format by example ("For example, Aug 3, 2026") and never scolds. A label is never inside the box: a placeholder carrying the label vanishes the moment typing starts, and the person who most needs it is the person who paused.

The rule, and the anti-rule

Use a text input

An open value the product cannot predict. "Cerebro Cloud" is the real string on add-subscription-empty, the state that exists precisely because a service is not in the preset catalogue of 400+. Anything a person might type and we could not have listed belongs here.

Use a select instead

A value from a closed list is the Select, not this. Billing frequency has five values and the product has to understand every one of them, so typing "monthly-ish" has to fail, and a control that lets a person write it is a control that has to reject them afterwards. Rejecting a person is expensive on the one screen whose job is to make the manual path feel cheap.

Ask once, in a field

The email on Settings, asked as a field with a label above it and nothing else in the row. One question, one control, one line of copy underneath if the answer needs a format.

Not for a yes or no

A preference that is on or off is the Checkbox inside a Switch row. It reads as a sentence a person agrees with, it needs no typing and no submit, and it cannot be filled in wrongly. A field asking "notify me? (yes/no)" is a question the interface already knows how to ask better.

A currency sign goes inside the box
$

The sign is part of the amount rather than a question about it, so it stands where the number stands and the person types digits only. Reach for .affix whenever the value is money, and only then. It is one class on the field and one span, and the box it draws is the same box every other field draws.

Any other unit stays outside it

For example, Aug 3, 2026

"a month", "in days", the shape of a date: none of these is part of the value, so none of them goes in the box. They belong to the label above or the hint below, where they can be a sentence a person reads once and where they do not eat the room the value needs at 360. A glyph inside the box is for a unit a person would otherwise have to type, and money is the only one this product has.

States

The sign adds no sixth state and changes none of the five. It cannot be hovered, focused or disabled, it repaints on nothing, and the ring that arrives on focus is the input's own and already wraps it. The states below are the states of a money field too.

Five states, and they exist because the input is interactive, not because the template has cells to fill. Each one is a token override rather than a style of its own: no hex and no number appears inside :hover or [aria-invalid], so the dark theme costs three lines in tokens.css rather than forty edits across the components.

The invalid state is authored, and it is the reason this component was worth writing carefully. A sweep of all 55 grey pages returns no aria-invalid, no required and no error class, and kit.css said so in the comment above the rule: "AUTHORED. A sweep of all 55 pages returns no aria-invalid, no required and no error class, so the kit would otherwise inherit an input that cannot be invalid. Clay, never red. The hook is the native attribute, so no page needs a new class." So the state is real, it is in the system, and no screen uses it yet. It is waiting for markup, which stage 09 or the rollout will give it, and until then it moves zero pixels.

Rest, live

The second one is genuinely invalid, by the native attribute, and the third is genuinely disabled, by the attribute rather than by a class the product does not carry. Faking a state with .is-invalid would document something the product cannot do.

The five, in both themes

The states are described, not photographed. Founder's decision, 2026-08-11: the snapshot strip went from every page in this kit, 120 images across 18 pages. They were framed as measurements rather than illustrations, and that framing was honest, but the bill came due all session: a value moves, and every picture of it is quietly stale until somebody re-shoots it. A stale picture is worse than no picture, because it looks checked. What is left is what a picture never carried anyway: the state, and the token it reads. The resting component is live and interactive above, so hover it, tab to it, and read the value off the real thing rather than off a photograph of it.
